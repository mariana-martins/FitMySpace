# Contributing & Accessibility

The rules of the design system live in one place, [`AGENTS.md`][agents], which people and coding
agents both read. This page does not repeat them: it is the order to work in, with a link to the
rule behind each step. When a rule changes, it changes there.

## A new component, step by step

- **1. Check the pattern first.** Read [`Button`][button], the reference implementation, and the
  component closest to the new one (`Dialog` for an overlay, `Tooltip` for something that
  floats). Check the roles, attributes and keyboard behaviour on MDN and in the ARIA Authoring
  Practices before writing the API. [Design system rules →][rules]
- **2. Tokens.** Add a tier-3 token for every value the component draws, pointing at a tier-2 role
  (add the role first if it is missing), then run `npm run tokens:build`. Every size, spacing
  and duration is a multiple of 4. Add the new colour pairs to `tokens.contrast.test.ts`.
  [Token rules →][rules]
- **3. Files.** One folder in `ui/` with `Name.tsx`, `Name.types.ts`, `Name.module.css`,
  `Name.test.tsx`, `Name.stories.tsx` and an `index.tsx` barrel, plus one line in the entry
  point `index.ts`. `ref` is a prop, not `forwardRef`. Icons come from the `Icon` registry,
  screen-reader text from `VisuallyHidden`. [Folder and API rules →][rules]
- **4. Stories.** The same order and shape as the `Button` stories, with a description for every
  control. A `play` that clicks or types goes in a hidden `Interaction (Test Only)` copy.
  [Story rules →][rules]
- **5. Patterns.** If a pattern drew around the missing component, switch it to the new one, take
  it off the Overview's "Not in the design system yet" list, and link the pattern from the
  component page under `### Patterns`. [Pattern rules →][rules]
- **6. Checks.** Run the checks below, look at the result in Storybook, and open a pull request
  that answers "Breaking?". [Checks →][checks] · [Git and breaking changes →][git]

## Accessibility

Every component meets [WCAG 2.2 AA][wcag]. [Accessibility rules →][a11y]

- **Semantic HTML first**, ARIA only when no native element fits.
- **Contrast:** 4.5:1 for text, 3:1 for borders, focus rings and other parts of a control, in
  every state.
- **Keyboard:** everything works without a mouse, and focus is always visible.
- **Labels and errors:** every control has a visible label; an error names the field, says how to
  fix it and never relies on colour alone.
- **Preferences:** respect `prefers-reduced-motion` and `forced-colors`.

What the tools check, and what they cannot:

- **axe in every story** (`npm run test:storybook`): any violation fails the run.
- **`jest-axe`** (`npm test`): violations in each state the component tests render.
- **Contrast pairs** (`tokens/tokens.contrast.test.ts`): hover, active and focus colours, which
  axe never sees in a story.
- **By hand, in the browser:** focus order, what a screen reader announces, and reading order. No
  tool checks these.

## Checks

- `npx tsc --noEmit -p .`: types.
- `npm run lint`: ESLint.
- `npm run lint:css`: Stylelint, for class names and unknown or tier-1 tokens.
- `npm test`: Jest, for components, tokens, breakpoints and contrast.
- `npm run test:storybook`: story `play` tests and axe.
- `npm run tokens:check`: `tokens.css` and `tokens.docs.json` match the JSON.
