# FitMySpace: Design System Architecture Plan

This document outlines the step-by-step execution plan for building the foundational Design System for the FitMySpace project. The goal is to create a highly scalable, accessible, and well-documented component library living within the main Next.js repository.

## Design Philosophy & Language
* **Vibe:** Serene, clean, and cozy. Designed to reduce cognitive load and promote a sense of organization.
* **Palette:** Pastel backgrounds (e.g., Sage Green) paired with deep, high-contrast text colors (e.g., Charcoal/Dark Moss) to strictly meet WCAG 4.5:1 contrast ratios.
* **Typography:** DM Sans (sans-serif) for a modern, legible, and warm feel.
* **Spacing Scale:** Strict 4px mathematical scale (4, 8, 16, 24, 32, etc.).
* **Styling Approach:** Styles will be consumed via native CSS variables generated by Style Dictionary (e.g., `var(--fms-semantic-color-...)`).

## Token Architecture (Brad Frost's Methodology)
Tokens will be managed via JSON and processed using Style Dictionary to generate native CSS variables.
* **Tier 1 (Core Tokens):** Literal values (e.g., `color.sage.100: "#e3efe9"`, `spacing.4: "16px"`). The AI assistant (Antigravity) will be used to help generate and implement this foundational tier.
* **Tier 2 (Semantic Tokens):** Intent-based aliases (e.g., `color.background.page` points to `color.sage.100`). This tier will be implemented manually by the developer to ensure architectural control.
* **Tier 3 (Component Tokens):** Component-specific aliases (e.g., `button.primary.backgroundColor` points to `color.text.primary`). This tier will also be implemented manually by the developer.

## Execution Steps

### Step 1: TypeScript Refresher (Completed)
* Solidified advanced TypeScript concepts for React component architecture.
* Focus areas: Interfaces vs. Types, Polymorphic components (`as` prop), Utility types (`Pick`, `Omit`, `Record`), and strict literal types (`as const`).

### Step 2: Requirements and Visual Scope Definition (Completed)
* **Design Tokens Defined:** 4px scale, DM Sans, serene/pastel palette.
* **Phase 1 Components Mapped:**
    * **Typography:** Polymorphic component supporting dynamic tags (`h1` through `h6`, `p`, `span`) with consistent styling.
    * **Button:** Variants (`solid`, `outline`, `ghost`), states (`default`, `hover`, `active`, `disabled`, `focus`).
    * **Inputs & Checkboxes:** Focus rings for keyboard navigation, error states for validation, and strict label associations.
* **API Design:** Components will extend native HTML attributes using `React.ComponentPropsWithoutRef`, omitting restricted props where necessary to enforce architectural safety.

### Step 3: Infrastructure and Tooling Setup (Completed)
* **Repository:** Internal monorepo structure (e.g., `src/design-systems/`) within the main Next.js App Router project.
* **Next.js Integration:** All interactive UI components will include the `"use client"` directive at the top of the file.
* **Required Dependencies to Install:**
    * `@storybook/nextjs` & `storybook` (For component isolation and documentation)
    * `style-dictionary` (To process JSON design tokens)
    * `@radix-ui/react-slot` (For polymorphic component rendering)
    * `@radix-ui/react-checkbox` & `@radix-ui/react-label` (For unstyled, A11y-compliant primitive base)

    #### Folder Structure & Colocation Strategy
To maintain a scalable and modular architecture, we will use a strict colocation pattern based on CSS Modules. Storybook stories, styles, and test files must live alongside their respective components, not in a separate global folder.

**Target Architecture:**
* `/components/design-system/tokens/`: Will hold all JSON token files (Tier 1, 2, and 3).
* `/components/design-system/ui/`: Will hold individual folders for each component.
    * Example: `/components/design-system/ui/Button/` will contain `index.tsx`, `Button.tsx`, `Button.module.css`, and `Button.stories.tsx`.
    * **Barrel Pattern Rule:** Every new component created in the `ui/` folder must include an `index.tsx` file to centralize local exports and named type exports.
    * **Types Extraction Rule:** Simple typings can start within the main component file. As TypeScript code volume grows (handling variants, polymorphism, etc.), typings must be extracted into an isolated `[ComponentName].types.ts` file within the component's folder. The local `index.tsx` file must always export the component and explicitly export its types using the `export type` directive.
* **Storybook Config (`.storybook/`)**
    The Storybook configuration ensures a robust, accessibility-focused environment strictly adhering to the Design System:
    * **Path Tracking (`main.ts`):** Storybook tracks only the stories residing in the `../src/components/design-system/` folder, ignoring default examples.
    * **Addons & Plugins (`main.ts`):**
        * `@storybook/addon-a11y`: Audits accessibility directly in the Storybook UI.
        * `storybook-addon-pseudo-states`: Allows visual testing of `:hover`, `:focus`, `:active` states, etc.
        * `@storybook/addon-docs`: Automatically generates documentation pages.
        * `@storybook/addon-vitest`: Integration with unit tests.
        * `@chromatic-com/storybook`: Setup for visual regression testing.
    * **Preview & Styling (`preview.tsx`):**
        * **Tokens Import:** Mandates the import of the auto-generated `tokens.css` to provide native CSS variables.
        * **Dedicated Fonts:** Loads the `DM Sans` font via `@fontsource` exclusively for the Storybook environment (the Next.js app uses Inter).
        * **Global Decorator:** Wraps stories with semantic text color variables (`--ds-semantic-color-text-default-base`).
        * **Story Sort:** Defines a fixed, cohesive sidebar visualization architecture: `Introduction` -> `Foundation` (Color, Spacing, Radii) -> `Components` -> `Patterns`.
        * **Strict A11y:** Configured with `test: 'error'`, meaning accessibility (WCAG) violations will cause automated validations to fail.
### Step 4: Component Construction (Completed)
* Build the Tier 1 components using the defined tokens and CSS Modules.
* Ensure all components properly extend native HTML elements to inherit default behaviors.
* Focus on clean component APIs, leveraging TypeScript Generics and `Record` utilities for variant mapping.
* **Strict MDN Verification Rule:** Whenever a new component is created, the AI assistant must proactively query the MDN documentation (via the MCP tool) to verify ARIA guidelines and DOM typings. This ensures the component's interfaces accurately extend the correct native DOM typings (without missing or exposing unnecessary attributes) and strictly follow the state-of-the-art accessibility standards for interactive elements.

### Step 5: Accessibility (A11y) and Testing (The Gold Standard)
* Conduct strict accessibility audits on every component (focus management, ARIA roles).
* Test keyboard navigation explicitly (Tab, Space, Enter).
* Write foundational unit tests using Jest and React Testing Library to prevent future UI regressions.

### Step 6: Documentation
* Finalize the Storybook documentation with clear examples, interactive controls, and API guidelines.

### Step 7: App Integration & Smart Components
* **Strict Boundary:** The Design System (`src/components/design-system/`) is strictly for "Dumb/Presentational" components. They must be completely unaware of application state, business logic, APIs, or data fetching. They receive data solely via `props` and communicate out via `callbacks`.
* **Smart Components:** Application-specific logic lives outside the Design System (e.g., `src/components/organisms/`, `src/app/`). These "Smart Components" import the dumb UI components and connect them to data sources, state management, and business rules.
* **Composition:** Following Brad Frost's Atomic Design principles, complex organisms and templates are formed by composing primitive design system atoms and molecules, keeping the separation of concerns clear and the foundational UI easily testable in Storybook.

### Step 8: Component Recipes & Composition Patterns
* **Recipes as Documentation:** Instead of building rigid, monolithic macro-components (e.g., a massive `<LoginForm />` with dozens of props), document **Recipes** in Storybook. Recipes demonstrate how to compose smaller primitives (Atoms and Molecules like `Input`, `Label`, `Button`) to solve common UI patterns.
* **Avoid Prop Overload:** Encourage composition over configuration. If a card needs an image, title, and actions, favor modular children (`<Card><CardImage/><CardBody/></Card>`) rather than a single component with excessive conditional props.
* **Maintainability:** Documenting these recipes in Storybook ensures developers know the "FitMySpace way" to assemble UI without cluttering the Design System's CSS Modules with highly specific, one-off overrides.

### Versioning and Commits

* **Conventional Commits:** The project strictly enforces the [Conventional Commits](https://www.conventionalcommits.org/) standard. All commit messages are automatically validated by Husky before being saved.
* **Automated Releases:** New versions, Git tags, and the `CHANGELOG.md` updates must be generated exclusively through the automated release process by running `npm run release`. Manual version bumps or changelog edits are prohibited.
